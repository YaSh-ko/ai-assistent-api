# Аутентификация API (Delёz)

## Сессии и JWT (RS256)

После успешного входа (`POST /auth/sign-in/email`) сервер выдаёт **сессионный токен** в виде **JWT**, подписанного алгоритмом **RS256** (RSA с SHA-256).

- **RS256** — асимметричная подпись: приватный ключ известен только API, публичный ключ можно распространять другим сервисам для **проверки подписи** без доступа к секрету подписи.
- Токен передаётся клиенту в теле ответа (`session.token`) и дублируется в **HttpOnly cookie** `session_token` (как и раньше).
- Для запросов к защищённым эндпоинтам можно передавать тот же токен в заголовке:  
  `Authorization: Bearer <jwt>`.

### Полезная нагрузка JWT (claims)

| Claim | Назначение |
|--------|------------|
| `sub` | ID пользователя (`user.id`) |
| `sid` | ID сессии в БД (`session.id`) |
| `exp` | Срок действия (Unix time) |
| `iat` | Время выпуска |
| `iss` | Издатель (если задан `JWT_ISSUER`, по умолчанию `delez-api`) |
| `aud` | Аудитория (только если задан `JWT_AUDIENCE`) |
| `token_use` | Тип токена: для сессии всегда `session` (новые выпуски); старые JWT без этого поля могут ещё приниматься при проверке подписи |

Запись сессии по-прежнему хранится в таблице `session` (отзыв при выходе, срок жизни, аудит). Строка JWT целиком сохраняется в поле `session.token`.

### Безопасность и поведение проверки

- Поддерживается только **RS256**; список алгоритмов при `decode` зафиксирован.
- Длина строки токена ограничена до декодирования (защита от чрезмерно длинного ввода).
- Сравнение выданного JWT с значением в БД выполняется **постоянным по времени** способом (`secrets.compare_digest`), если длины совпадают.
- **`JWT_LEEWAY_SECONDS`** (по умолчанию `120`) — допустимый сдвиг часов между клиентом и сервером при проверке `exp` / `iat` (и смежных проверок PyJWT).
- Если строка **похожа на JWT**, но публичный ключ не настроен, запрос **не** обрабатывается как opaque-токен: возвращается ошибка авторизации (исключает подбор по БД при неверной конфигурации).
- При отсутствии ключей подписи новая сессия **не создаётся**: ответ **503** с понятным сообщением (см. `JwtConfigurationException`).

### Обратная совместимость

Ранее выдавались **непрозрачные** случайные строки (`secrets.token_urlsafe`). Такие токены по-прежнему принимаются, пока сессия есть в БД. Новые сессии создаются только как **RS256 JWT** (при настроенных ключах).

## Настройка ключей (production)

1. Сгенерировать пару RSA (пример):

   ```bash
   openssl genrsa -out jwt_private.pem 2048
   openssl rsa -in jwt_private.pem -pubout -out jwt_public.pem
   ```

2. Передать содержимое PEM в переменные окружения:

   - `JWT_PRIVATE_KEY_PEM` — полный текст приватного ключа (включая `BEGIN/END`).
   - `JWT_PUBLIC_KEY_PEM` — полный текст публичного ключа.
   - `JWT_ISSUER` (опционально) — строка издателя, должна совпадать при подписи и проверке.
   - `JWT_AUDIENCE` (опционально) — если задано, в токен попадает claim `aud` и он **обязателен** при проверке. Включайте только если все клиенты готовы к фиксированному audience; иначе оставьте пустым.
   - `JWT_LEEWAY_SECONDS` (опционально, по умолчанию `120`) — допуск по времени в секундах.

В `.env` многострочный PEM часто задают с переводами строк как `\n` в одной строке или через секреты оркестратора. Приложение при старте нормализует литеральные `\\n` в реальные переводы строк.

### Ротация ключей

1. Сгенерируйте новую пару RSA, пропишите новые `JWT_*_PEM` на всех инстансах API **одновременно** (или через общий секрет-менеджер).
2. После смены ключей все **старые** JWT перестанут проходить проверку подписи — пользователям потребуется повторный вход (новые сессии подписываются новым ключом).
3. Для «мягкой» ротации потребовались бы несколько активных публичных ключей (kid/jwks) — в текущей схеме это не реализовано.
